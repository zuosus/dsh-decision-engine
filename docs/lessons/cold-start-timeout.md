/**
 * 同一个端点，浏览器 200 而 Node fetch 报错——不是「Node 不行」，是四类失败被
 * 混成了同一个「报错」。
 *
 * 用户原话：
 *
 *   「官方文档页点『发送请求』永远返回 200，在插件里配好同一 provider 点
 *     『测试』大约 2/3 会报错。」
 *
 * 2026-11 实测（bamboonode `https://api.bamboonode.dev/v1/decisions`，
 * 模型 startlux-decision-27b-autothink，生产遥测 2573 次请求 / 358 次降级）：
 *
 *   场景                              实测延迟
 *   ────────────────────────────────  ────────────────────────────────
 *   闲置 110 秒后首发                 7.4–15.9 s（服务端冷启动尾延迟）
 *   焐热之后                          1.0–1.3 s
 *   首发被掐断后的第二发              1.1–1.7 s，4 组独立实验一致
 *   thinkMode: never / auto           约 1.9 s / 约 7.2 s
 *
 *   成功请求延迟分布（n=2215）：
 *     <1s 36.1% | 1-2s 31.8% | 2-4s 18.3% | 4-6s 8.8% | 6-8s 5.0% | ≥8s 0%
 *
 * 注意最后那个 0%：**不是没有慢请求，是慢的那些全被 8 秒预算掐掉了**，
 * 根本没资格算进「成功」。只看成功样本会得出「这个端点从不超 8 秒」的错觉。
 *
 * 四类失败：判别特征与修复动作完全不同
 * ---------------------------------------------------------------------------
 *   类别      判别特征                            修复动作
 *   ────────  ──────────────────────────────────  ──────────────────
 *   超时      耗时卡在预算线整数值                抬 timeoutMs；
 *             （如 8000 / 8001 / 8002 / 8003，    冷启动首发值得重试
 *             本机实测 123 次全聚在 7999–8005）
 *   网络错误  错误文本 `fetch failed`，           换链路 / 查代理；
 *             耗时 5 秒上下（实测 5004–5557 ms）  重试同样有效
 *   5xx       带服务商自己的 JSON 错误体：        本地改不了；
 *             `{"error":"Task request failed"}`   降级放行即可
 *             `{"error":{"message":"Database
 *              error, please contact the
 *              administrator (request id: …)",
 *              "type":"new_api_error"}}`
 *   冷却      耗时 0–1 ms                         等冷却结束；
 *             （本机 113 次：0 ms×106、1 ms×7）   半开试探可消除
 *             请求根本没发出去
 *
 * 这四类混成一句「测试失败」，用户唯一能做的动作就是反复点「测试」——
 * 而反复点恰好每次都采在最差点上（见下）。所以判别的第一步永远是**看耗时**：
 * 0 ms 说明请求没发出去，8 秒整数说明被自己的预算掐了，5 秒上下且
 * `fetch failed` 说明链路层就没通，带 request id 的 JSON 才是服务端自己的事。
 *
 * 为什么「点测试」永远看到最坏情况
 * ---------------------------------------------------------------------------
 *
 * 「测试」是手动触发的，而人点它的时机是「刚想起来 / 刚改完配置」——也就是
 * 端点**闲置了一段时间**之后。每一次点击都是一次冷启动首发，等于永远在延迟
 * 分布的最右端采样。真实降级率是 **13.9%**（2573 次请求 / 358 次降级），
 * 不是 2/3；2/3 是这个采样偏差的产物，不是端点的属性。
 *
 * 358 次降级的构成：timeout 83 | network-error 84 | http-5xx 95 | cooldown 93
 * | caller-aborted 2 | 429 1 | 502 1 | 530 2。
 *
 * 顺带一个放大器：连续 3 次失败进入 60 秒冷却，而一次抖动往往 3 秒就过去了。
 * 于是「3 秒的服务端抖动」被放大成「60 秒完全不工作」，冷却期间的请求以
 * 0 ms 计入降级——它把一次小故障记成了一串大故障。
 *
 * 代理：能解释一部分网络错误，但不是可靠修复
 * ---------------------------------------------------------------------------
 *
 * 浏览器那一侧为什么看起来更皮实：文档页的按钮**没有短超时**（实测 15.9 秒
 * 也照等），并且走系统代理（Clash 127.0.0.1:7897），连接重置会被透明重试。
 * 插件是 Node fetch、直连、POST 不重试、外加 8 秒硬预算——三条差异叠起来，
 * 同一个端点在两边表现完全不同。
 *
 * 关于代理，有三条容易记反的事实：
 *
 *   1. **给 Node fetch 设 `HTTPS_PROXY` 环境变量是无效的**。Node 的 fetch
 *      不读它。实测反而变成 `UND_ERR_CONNECT_TIMEOUT`（10.5 秒）+ 连续
 *      ECONNRESET——比不设还差。
 *   2. **Node 26 起 `NODE_USE_ENV_PROXY=1`（或 `--use-env-proxy`）才真正生效**。
 *      实测某次 4001 ms → 1949 ms，确实是改善。
 *   3. **但在冷启动场景代理并不稳定优于直连**：同一次实验里 8030 ms（代理）
 *      vs 6035 ms（直连）。所以代理是**环境相关的诊断手段，不是可靠修复**。
 *      本机 DNS 解析到 198.18.0.145（Clash fake-IP），这本身就说明链路被
 *      本机代理接管过——排查时先确认这一层在做什么，再谈插件的问题。
 *
 * 可靠修复是**重试**：首发被掐断时服务端其实已经被焐热了，第二发 1.1–1.7 秒
 * 必中（4 组独立实验一致）。只对 timeout / network-error 重试，4xx / 5xx
 * 不重试——配置错和服务端故障重试只是多烧一次额度、拿回同一个错误。
 *
 * 一条可直接跑的自查命令
 * ---------------------------------------------------------------------------
 *
 * 失败记录的特征是 **`action: "degraded"`**，不是某个布尔字段（明细文件里的
 * `degraded` 是另一套口径，别拿它过滤遥测）。先按 detail 分类计数：
 *
 *   jq -r 'select(.action=="degraded") | .detail' \
 *     ~/.dsh/dsh-decision-engine/telemetry.jsonl | sort | uniq -c | sort -rn
 *
 * 再加一列耗时，四类失败立刻分开（同一条记录里的 `latencyMs` 就是判别特征）：
 *
 *   jq -r 'select(.action=="degraded") | "\(.detail)\t\(.latencyMs // 0)"' \
 *     ~/.dsh/dsh-decision-engine/telemetry.jsonl \
 *   | awk -F'\t' '{c[$1]++; s[$1]+=$2;
 *        if(!($1 in mn)||$2<mn[$1])mn[$1]=$2;
 *        if($2>mx[$1])mx[$1]=$2}
 *      END{for(k in c) printf "%-16s %5d 次   耗时 %6d-%-7d ms\n", k, c[k], mn[k], mx[k]}' \
 *   | sort -k2 -rn
 *
 * 实跑输出（本机 telemetry.jsonl，窗口与上文的 2573 次不同，仅示范判读）：
 *
 *   timeout            123 次   耗时   7999-1007518 ms
 *   network-error      115 次   耗时   1076-7969    ms
 *   cooldown           113 次   耗时      0-1       ms
 *   http-500           109 次   耗时    258-7560    ms
 *   no-key              48 次   耗时      0-3       ms
 *   http-530             2 次   耗时   2316-4295    ms
 *   http-503             2 次   耗时     84-245     ms
 *   caller-aborted       2 次   耗时    453-1865    ms
 *   http-502             1 次   耗时   1257-1257    ms
 *   http-429             1 次   耗时   2883-2883    ms
 *   http-400             1 次   耗时     62-62      ms
 *
 * 判读：timeout 的 7999–8005 是 8 秒预算的形状（两个 >10s 的离群值是进程被
 * 挂起，不是网络）；cooldown 的 0–1 ms 证明请求没发出去；network-error 全部
 * 是 `fetch failed` 且聚在 5 秒上下，那是链路层在超时而不是服务端在回话。
 * 想进一步分 5xx 到底是谁的问题：
 *
 *   jq -r 'select(.action=="degraded" and (.detail|startswith("http-5"))) | .extra.body' \
 *     ~/.dsh/dsh-decision-engine/telemetry.jsonl | sort | uniq -c | sort -rn
 *
 * 带 request id 的 `new_api_error` 是服务商内部的数据库错误——本地无论怎么
 * 改配置都不会变好，只能等或换 provider。
 */
